# Changelog

## [Unreleased]

### Added

- Droid, Factory's CLI, drives the indicators through its own hooks. `droid` joins `busy_detection.ai_tools`, and `docs/AI_TOOL_HOOKS.md` carries the `~/.factory/hooks.json` to drop in: `UserPromptSubmit` raises the spinner, `Notification` raises the `?`, `Stop` rings the bell. Droid's events are named like Claude Code's, but two things differ. The event names sit at the top level of `hooks.json` with no `"hooks"` wrapper, and a wrapped file parses fine while firing nothing. And `Notification` covers `auth_success` as well as the three that actually want an answer, so the hook reads the type off stdin rather than putting a `?` on the window every time you log in.

  Adding `droid` to `ai_tools` is not optional decoration: the daemon clears `@tabby_busy` on a pane it does not read as an AI pane, so without it the spinner is set by the hook and taken off again on the next reconcile, while the bell survives — which looks exactly like a missing start event.

- `prefix + Y` sends the focused pane's last 100 lines to the clipboard of the device you are physically at, and `tabby clip send` does the same from a script, a pipeline, a file or a literal string. Drag-select already copied through OSC 52, but dragging a selection is not a thing you can do on a phone, and the machine running tmux is usually two hops below the clipboard that matters — so `pbcopy` on that machine writes somewhere nobody can paste from. This travels the same path as any other pane output: tmux, then mosh or ssh, then the terminal app. Nothing listens, nothing is forwarded, no port is opened.

  The client-\* boxes get it without the binary. `scripts/tabby-clip.sh`, sourced from a remote shell rc, defines `tabby-clip` and `tabby-clip-tail`, which emit the same escape in pure shell — byte-identical to the binary's, on both BSD and GNU base64 — and wrap it in a DCS passthrough envelope when the remote shell is itself inside tmux. That nested case needs `allow-passthrough on` on the remote tmux; without it the envelope is swallowed whole and nothing reports an error. Agents reach either form through `skills/tabby-clip/` and `commands/clip.md`, both of which probe for the binary and fall back to the shell function, so one pair of files copied into `~/.claude/` works on every host.

  Getting this to the far end of a mosh link needs `set-clipboard on` and nothing else. The widely repeated advice to supply tmux an `Ms` terminfo capability through `terminal-overrides` is stale: capturing the pty on 3.4 and on 3.6 shows the same bytes leaving tmux with the override and without it. [SSH and Remote Hosts](docs/wiki/SSH-and-Remote-Hosts.md#clipboard) has the detail, and the reason the reverse direction — reading your phone's clipboard from here — is not on offer.

- `landing.command` points a new tab at a launcher other than tabby's own. The value is a shell command line typed into the new tab's shell, so `command: eval "$(pounce --target current)"` hands the tab to that launcher and nothing in tabby knows or cares what it is. Still gated on `landing.enabled`, still off by default, and a tab that inherits an ssh connection still goes straight to the host. A value naming something absent costs one "command not found" and leaves a usable prompt.

  The sidebar's `+` now honours all of this too. It shares the decision with the `tabby new-window` spawner instead of restating it, which is also a fix: on any install without `bin/new-window` built, `+` fell back to a path that had never learned about landing, so the launcher appeared on `prefix + c` and not on the button.

- The cat keeps a permanent record. Time in each state, adventures and what came back from them, catches and escapes by species, care and adventure streaks, fastest yarn catch, favourite biome, longest nap, worst neglect — it all accumulates under `lifetime_stats` in `~/.local/state/tabby/pet.json`. Rates and rankings are computed on read rather than stored, so a counter fix never leaves a stale number behind. An older `pet.json` loads unchanged: the counters start at zero and the birthday is backdated to first sight (#25).

- Cats bring you things. A successful pounce on an adventure sometimes gets carried home and left on the ground; click it to accept and the cat is pleased with itself, or it takes the gift back after ten minutes. Three at a time, oldest first out (#28).

- On an adventure the cat now hops over rocks, logs and trees instead of walking through them, and about a third of the time climbs one and sits up there a while before carrying on (#28).

- `auto_theme.sync_claude_code` mirrors the light/dark toggle into Claude Code's own theme setting in `~/.claude/settings.json`. Off by default. Preserves the `-ansi` and `-daltonized` variant of whatever theme is already set. Claude Code reloads the file, so running sessions repaint without a restart.

### Changed

- The two AI attention indicators now mean different things and clear differently. The diamond is a notification: an AI pane that finished working while you were on another window raises it, and switching to the window clears it. The `?` is an unanswered question, so it survives you reading it and clears when the tool starts working again — which is what happens when you reply. Deciding between them needs to know whether the tool actually asked anything, so when a pane stops working the daemon reads its last 40 rows once and looks for question phrasing, a boxed list of numbered choices, or a closing line that ends in `?`.

  Before this, `?` appeared on any AI pane that was merely sitting at its idle glyph and was dismissed by looking at the window, which is backwards on both counts: a Claude Code tab parked with nothing to do carried a permanent `?`, and a real question was cleared by switching to the window without answering it. The diamond, meanwhile, only ever meant the tool had exited, and the in-memory expiry re-asserted it every poll — so visiting the window unset the tmux option and the diamond came straight back on the next cycle.

- Whether an AI pane is working is now read from the pane, not just its title and its hooks. Claude Code prints a status line above its input box with a counter that ticks while a turn runs (`✽ Symbioting… (27s · ↓ 1.2k tokens)`) and stops when it ends (`✻ Brewed for 2m 29s`), and that counter now outranks every other signal. It has to: a tool that sets its own pane title sets it to something durable, so a pane titled `✳ fix-manifest-archive-scheme` says exactly that whether it is mid-turn or has been sitting idle for an hour. With nothing to contradict them, the hooks were the only vote — one missed `Stop` and a window kept its diamond for the rest of the session, and a hook-set `?` could sit on a pane that had long since been answered and gone back to work. The reading is cached for a second, so a burst of reconciles still costs one `capture-pane` per pane per second.

- Each tmux hook tabby installs now runs as a single background job wherever ordering allows, and the tabby subcommands inside it as one process. A hook body ending in `;` is several `run-shell -b` commands, and tmux makes a separate job — a `socketpair()` plus a forked shell — out of each one, so `after-select-window` cost three jobs and three `bin/tabby` execs and `client-attached` cost five and four. They now cost one and one: the steps are joined into a single body, and a new `tabby batch -- <sub> -- <sub>` subcommand runs the several subcommands in one process, `--`-separated, so one segment failing does not abandon the rest. `client-resized` drops 2/2 to 1/1, `session-created` and `window-unlinked` drop from two jobs to one each, `after-kill-pane` keeps two because its first step must stay a synchronous `run-shell` (pane ratios have to be recorded before the reflow), and `client-active` and `client-focus-in` (1 job and 3 execs apiece, on every focus change) are gone. Hooks fire once per session a window is linked into, so on an 8-session group these are per-event savings multiplied by eight.

  Collapsing `client-attached` also fixes a real ordering bug. Its five jobs were concurrent, so `ensure-daemon.sh` had no ordering guarantee over the four steps that need the daemon to exist; in one body the shell runs them in written order.

  The five hooks that overlapped between `tabby.tmux` and the daemon's own registration were being defined twice, and `set-hook -g` replaces rather than merges — so whichever ran last won, and a daemon start silently reverted the config's copy. There is now one definition table, in `cmd/tabby/internal/tmuxhooks`, which `tabby.tmux` installs through `tabby install-hooks` and the daemon and watchdog call directly.

- `stripAnsi` no longer rebuilds its regular expression on every call. Four packages carried an identical copy with the `regexp.MustCompile` inside the function body, so the pattern was parsed and compiled once per line, per widget, per frame, and the sidebar strips every line it is about to measure. One shared `internal/ansi.Strip` replaces all four, hand-rolled rather than regex-based, returning the input untouched when it holds no escape at all. Coloured text goes from 1549ns and 26 allocations per call to 91ns and one; a line with no escapes goes from 1549ns to 3.3ns and no allocation. A fuzz run of 2.8 million inputs confirms it agrees with the pattern it replaces byte for byte, including on truncated and non-SGR sequences. `extractPaneArg` had the same fault with three patterns and got the same treatment.

- The daemon can profile itself. Set `TABBY_PPROF_ADDR=127.0.0.1:6060` and it serves `net/http/pprof`, off otherwise, and refused outright on any non-loopback address since the endpoints expose memory contents on a process that runs unattended for days. This exists because macOS `sample` walks a Go process down to `runtime.asmcgocall` and stops, reporting where the runtime parked a goroutine instead of which ticker is spending the time, which is how an earlier guess at this daemon's idle CPU landed on the wrong subsystem.

- The geometry tick no longer reconciles because a clock moved. It runs every 250ms and forks a `tmux list-clients` each time, and its dedup key carried the elected client's activity timestamp divided by five. So on any machine where a pane is always drawing, a log tail or an AI session, that bucket rolled forever and every few seconds the daemon ran a full `ForceWidthSync` reconcile that re-synced widths to the values they already held. Measured on a nine-session group: one reconcile every 5 to 13 seconds, indefinitely, with the tty and the size identical in every log line. An activity-only wake now updates the active-client snapshot and stops there, and the reconcile behind it is rate-limited to once every 30 seconds rather than dropped, because it had also become the periodic full refresh other state leans on. Measured after: one every 53 seconds.

  The tick itself also backs off now, from 250ms to a ceiling of 2 seconds, after twelve consecutive passes that find nothing to do. Any priority event resets it, meaning any renderer input or tmux hook, so a client the user is touching pulls the poll back to full rate before that action's consequences need noticing. That is what makes backing off safe with several clients attached, since the case the poll uniquely catches is the active-client election flipping between them. A resize arrives through tmux's own `client-resized` hook regardless. On an idle daemon the subprocess rate drops from 2.3/s to 0.8/s; while you are working it correctly stays at the base rate.

### Fixed

- Window and pane hooks no longer fire in sessions that have no daemon to hear them. tmux fires these once per session a window is linked into, but in a grouped set only the sessions someone actually runs tabby in have a daemon; the rest are along for the ride because they share the window list. Every one of those fires forked a shell, read a pid file that was not there, and exited. On the 9-session group this was measured on, one `new-window` drove 514 `hook-notify.sh` runs and a create-then-kill cycle drove 915. The same two operations now cost 10 and 75.

  The gate is a tmux format, `#{?#{&&:#{!=:#{@tabby_daemon},},#{!=:#{@tabby_mute},#{session_id}}},1,0}`, so the server answers it itself and a closed gate spends no job, no socketpair and no fd — which is the same ceiling the fd-exhaustion fix above is about. A daemon sets `@tabby_daemon` on its own session at startup and unsets it on the way out. It has to be a session option and not a server one: a server-wide flag would say only "some daemon is running somewhere", which in a grouped set is true the moment any one session starts one, and the gate would be open for all nine again.

  Only hooks whose trigger is a window- or pane-level change sit behind it (`window-linked`, `window-unlinked`, `after-new-window`, `after-split-window`, `after-kill-pane`, `after-resize-pane`, `after-resize-window`). Those events are shared by the whole group, so the daemon's own session fires the same hook for the same event and dropping the peers' copies loses nothing. The client- and session-level hooks keep the plain mute gate: they fire in one session only, which may be a daemonless peer whose request `dialDaemon` hands to a peer daemon, and `client-attached`, `session-created` and `client-session-changed` are what start a daemon in the first place, so gating them on one existing would be a deadlock.

  Every failure mode is fail-open or self-correcting. A daemon killed without unsetting the option leaves the gate open, which is the behaviour that shipped before this. A daemon still starting has not set it yet, so a handful of fires are skipped, and its own reconcile tick covers them.

- tmux no longer prints `'/Users/.../scripts/hook-notify.sh' returned 1` or `failed to run command: /Users/.../hook-notify.sh` over the screen while you work. These look like one bug and are two, neither of them in the script: it ends in an unconditional `exit 0` and cannot return 1.

  `returned N` comes from the child tmux forks per `run-shell`, which exits 1 through `fatal()` if anything between the fork and the exec fails: the chdir, a dup2, opening `/dev/null`, the exec of `default-shell`. The body never runs, so appending `; true` to it changes nothing, which is why the message survived that first fix. `run-shell` is the only form that reports a job's status at all. `if-shell` runs the same job and takes its else branch when the status is nonzero, silently, so the backgrounded housekeeping hooks are now `if-shell -b '<body>' ''` with an empty else. The foreground hooks that later steps order against stay as `run-shell`.

  `failed to run command` is raised before any job exists, when `job_run()` gets a failure from `socketpair()` or `fork()`, and no hook body in any form can suppress it. The cause is fd exhaustion in the server. Hooks fire once per session a window is linked into, and every `tmux` call inside a body is a client connection holding a server fd until it exits, so the cost of one new-window scales with the size of the session group: on an 8-session group a single new-window fires `hook-notify.sh` 16 times and took a live server from 41 open fds to 234, against a soft `RLIMIT_NOFILE` of 256. Past that ceiling the server also stops accepting new client connections, so `tmux ls` answers "no server running" for as long as the burst lasts.

  `hook-notify.sh` now takes `#{session_id}` and `#{session_attached}` as arguments, expanded by the server for free while it dispatches the hook. That drops the `tmux display-message` it used to run to find its own session, and skips the `tmux refresh-client` on a session with no attached client, where the call was already a silent no-op. Two client connections per fire become at most one, and none on the sessions nobody is looking at. It also signals the daemon inline instead of exec'ing `signal-daemon.sh`, one fewer process per fire; `signal-daemon.sh` stays for the mouse bindings, which have no session id to hand.

  Since 256 is the macOS default (`launchctl limit maxfiles`) and tmux never raises it, the plugin now reads the server's limit during init and says so once per server if it is under 1024. The fix is a `ulimit -n 8192` in your shell rc and a fresh tmux server.

- The daemon no longer fires tabby's hooks at itself. Cheapening each fire was only half the problem; the other half is how many there are. On a nine-session group, one `new-window` was measured firing `window-linked` **495 times** — 66 distinct `(session, window)` pairs, the rest repeats, because tmux resyncs the whole shared window list to every session in the group and then attributes a further round to the newest one. Every fire is a hook body, so every fire is a `socketpair()` and a forked shell, which is how a single window ends up spending most of a 256-fd budget. `coordinator.go` already knew about part of this — the cycle decomposition that turns 2N `move-window`s into N+c exists because each move fires both `window-linked` and `window-unlinked`, each of which signals the daemon to re-run `syncWindowIndices` — but that counts fires per move and misses the per-session multiplier, which on this group is another factor of nine.

  Every hook tabby installs now sits behind `if-shell -F '#{?#{==:#{@tabby_mute},#{session_id}},0,1}'`, and the daemon writes its own session id into `@tabby_mute` around its own tmux mutations. The gate has to be an `-F` format: tmux evaluates it inside the server, so a muted hook costs a string comparison and never reaches `job_run()` — by the time a script could read the flag, the socketpair and the fork have already happened.

  The gate names a session rather than being a boolean, and that is the whole of its correctness. tmux options are per-server; tabby's daemons are per-session. A boolean `@tabby_mute` muted every daemon in the group at once, so the peers never heard about the window-list changes the muting daemon had just made and their models went stale — minimize left window state mixed across windows. Carrying the id means a fire is dropped only in the session whose own daemon caused it, and since `hook-notify.sh` signals the daemon of `#{session_id}`, every peer's notification still arrives. Both no-daemon values read as "run": an unset option expands to empty and clearing writes `0`, and neither can equal a session id, which is always `$N`.

  Scoping costs most of the boolean's headline number and is worth it. Measured on the same nine-session group with a counting probe on `window-linked`, one `new-window` fires 1134 times raw and 363 survive the gate — a 3.1× cut, where the boolean's was 21× (1445 → 68). The difference is exactly the eight peer sessions' fires, which are the ones that must not be suppressed. Server fd peak for one `new-window` is now 14 against an idle 11; before any of this work the same operation took the server from 41 to 234 against a 256 soft limit. The remaining 363 are dominated by sessions with no daemon at all, which still pay a fork to discover there is no pid file — a per-session "has a daemon" option in the gate would collect that, and is not done here.

  The gate is engaged lazily from the two places every daemon tmux call passes through, keyed off the verb — 18 window-list mutations, with `set-option` deliberately not among them, since the gate is itself a `set-option` — and released 150ms after the last one, re-armed by the next. The navigation verbs are not among them either. With `select-window` in the set, clicking a sidebar tab drew the previous window's contents inside the new window's border: the click asks the daemon to select a window, selecting closed the gate, and the `after-select-window` hook that selection fired — the one whose entire job is `refresh-client -S` — was muted, so the client went on serving the layout it already had. They earn nothing anyway; the amplification is all window-list churn, which tmux replays to every session in the group, while selecting fires one hook in one session. `-F` conditions are not backgrounded: `-b` on the gate buys nothing when there is no shell to background, and would defer the body by a queue turn, which is enough to reorder `after-kill-pane`'s synchronous first step behind the rest of its body.

  `@tabby_mute` outlives the process that set it, so a daemon killed mid-batch would otherwise silence its own session's hooks for the life of the server. It is cleared at daemon startup, on every path out of the watchdog, and by hook installation itself, which covers plugin load, `tabby toggle` and every watchdog restart. A daemon that cannot resolve its own session id does not engage the gate at all: an unsuppressed burst costs fds, an unscoped mute costs a peer its state. Concurrent daemons still share the one option, so the last writer owns it and a peer engaging its own mute lifts this one early — that direction only ever costs unsuppressed fires, and the next mutation re-engages. The cost of the gate is that a real user event landing in this session inside one of those 150ms windows is suppressed too; the daemon picks it up on the next reconcile.

- A minimized window shows up in the Minimized section on every window again, not just on the ones drawn by whichever daemon happened to park it. Each session in a group runs its own daemon, and they split the sidebar rendering between them, so the daemon drawing a given window's sidebar is usually not the one that did the minimize. The parked-window listing is memoized and was only ever invalidated in-process, by the local park and unpark paths, so a peer's daemon kept serving the list it read the first time it ever looked - on this machine, one from three days before the window was minimized. The entry now also ages out after two seconds, which is what catches a peer's park; a local minimize still invalidates immediately, so the section is instant on the windows you are looking at.

- The sidebar's `<` and `>` buttons resize the sidebar again, as do the `▲`/`▼` window-nav buttons and the theme toggle beside them. They rendered, they highlighted, and clicking them did nothing — the daemon never received the click at all, because the regions that make them clickable were never computed for the frame they belonged to. Widget click regions came from BubbleZone's `Scan` followed immediately by `Get`, but `Scan` hands its parsed bounds to a background goroutine, so `Get` reads whatever the *previous* scan stored: nothing on the first frame, and stale bounds after that. Compounding it, every `Scan` ends by deleting zones left over from other iterations, and the sidebar scans twice per frame — once for the top widget zone and once for the bottom — so the two scans erased each other's zones. The marker scan is now done inline and synchronously, against the exact content being returned.

- Minimizing the dashboard no longer destroys the session. Parking a window is `move-window -d` out of the session, and tmux ends a session whose last window leaves — which in a grouped session takes every peer down with it, since a group shares one window list. The dashboard is the last window by construction: `enterDashboard` gathers every content pane into it and kill-windows the emptied origins, and the origin names, colours and indexes it needs to undo that live only in the daemon's memory. So minimizing it ended the session, killed the daemon, and left `exitDashboard` with nothing to run against — the layout was unrecoverable. The dashboard, and a session's only remaining window, now refuse to minimize and say why in the status line.

- A minimized window whose origin session has died is now recoverable. Restoring is a `move-window` at the session named in `@tabby_min_origin`, and a tag naming a session that has since gone simply fails: the row sat in the Minimized section and did nothing when clicked. The fallback to the current session had only ever covered an *empty* tag, never a stale one. It now covers both, and the sweep that adopts stranded windows runs on the owner-gated watchdog tick as well as at daemon startup — the peers that strand windows here come and go long after any daemon started.

- Grouped sessions now see each other's minimized windows. The Minimized section listed a parked window only when `@tabby_min_origin` matched the current session id exactly, but grouped peers share one window list, so minimizing from one peer and looking from another showed nothing — the window was reachable only by returning to the exact session that parked it. Parking now records the origin's session group alongside its id, and the listing matches on either.

- A failed `list-windows` no longer takes the holding session down with everything parked inside it. `cleanupMinimizedSessionIfEmpty` asked whether any parked windows remained and read the error case as "none left", so one transient tmux failure ran `kill-session` on a session full of minimized windows. The limbo session's cleanup had the same shape behind its stashed-sidebar and content-stash checks. Both now tell "nothing there" apart from "couldn't look", and skip the kill on the latter.

- The pane title is back on phone clients, on the divider above the button bar. It had been switched off there to save a row, but the split still drew a separator line between the content pane and the button bar, so the row was being spent either way — the only thing lost was the window name and pane title, on the client with the least other chrome to tell one tab from another. Because the switch read the elected client's profile rather than each window's width, attaching a phone also stripped the title row from every desktop client sharing the session. Below 100 columns the label moves off the top of the screen onto that already-drawn divider, where it describes the window's active pane rather than the button bar it sits on, and the right-aligned `[prefix+, for actions]` hint — 23 columns against a 49-column window — drops.

- Dragging the sidebar and immediately switching windows no longer loses the drag. The two-pass adopt only armed its candidate once a pass saw the dragged window active; a fast switch meant no arming pass ever ran, and the first audit after the switch snapped the pane back to the stale global. The renderer's own resize report now arms the candidate, and a pending candidate is corroborated against the dragged window's live measurement even after the active window moved — with the profile/keyboard clamp shapes re-vetted so a clamp report can never be adopted as a drag.

- `exit-if-no-main` no longer kills a session on a failed pane listing. The hook read `list-panes` with its error discarded, so a transient tmux failure mid window-churn returned empty output, read as "no main pane", and ran `kill-session` on a healthy session — observed live as infras-24 destroyed under a create/kill burst, detaching its client. An error or empty listing now skips the kill.

- Double-click no longer risks taking the whole tmux server down. The double-click binding runs `copy-pipe-and-cancel` on a 0.3s delay; if the pane left copy mode or died during that delay — which window churn does routinely — tmux 3.6b segfaults in `window_copy_pipe_run`, killing every session on the server. The deferred pipe now re-checks the pane is still in copy mode, against the literal pane id captured at click time.

- A detached session's daemon no longer stays in phone profile forever. The geometry tick early-returns when its session has no attached clients, so the last client's width and profile survived the detach — and when that daemon later won the group layout lease it applied the departed phone's chrome to every shared window: sidebars stashed, widths clamped, tabs relabeled from raw pane text. The election now reports the attached-client count, and a genuine zero clears the cached client, returning the daemon to the desktop fallback.

- Sidebars a phone episode leaves stashed now restore themselves. The desktop transition that should un-stash them is skipped while the phone is still attached (`PROFILE_TRANSITION_SKIP_DESKTOP`), and once the phone detaches nothing re-fires it — the desktop owner's own profile never changed, so no transition was ever scheduled again. The owner-gated watchdog tick now reconciles the residue: desktop profile, sidebar mode enabled, stash windows present, no narrow client attached — restore.

- `tabby-watch.sh` no longer flags the watchdog pidfile as an orphan daemon; the orphan check globbed `/tmp/tabby-daemon-*.pid` and read `$24.watchdog` as a session name.

- Window switching no longer judders the sidebar width when idle grouped sessions are attached. Two loops fed each other: the park machinery stowed idle sessions onto the user's most-recent windows (history is MRU-first), and per-client nav then dragged every client pointing at the source window — parked phone sessions included — along with the user's keypress. Each hop re-clamped the window to the idle client's size and back, visibly flapping the sidebar through 1/15/51/60/74 columns before width-sync re-locked it. Parks now pick the least-recently-used window no session in the group points at, re-check the contest right before moving a session, and nav skips clients idle past the park threshold whenever an active client is on the source window.

- Picking up the phone now resizes the windows. In a grouped session the daemon that gains the layout lease re-locks every window to its client's size; before, the resize fired ~3s too early (while the phone's daemon was still a non-owner), got dropped, and left the group laid out for the desktop it just left — a 167-column window on a 67-column screen until something else changed size.

- Sidebar tab clicks now switch the clicking client's own session, not the sidebar-owner daemon's. Under grouped sessions (`new-session -t`) a window's sidebar pane is rendered by whichever daemon spawned it, and the click handler ran `select-window` scoped to that daemon's session — so clicking a tab in a peer-owned sidebar moved the peer's current window while the attached client saw nothing happen. The click path now finds the clients viewing the clicked window and `switch-client`s each of them, session-qualified, with the old global select as fallback — the same per-client model keyboard nav already used.

- Clicks land where you aim them again, and hooks stopped printing `returned 1` across the screen. Tabby registered its global tmux hooks from two places — `tabby.tmux` at plugin load, and the watchdog and `tabby toggle` each with their own copy of the table when a daemon starts. `set-hook -g` replaces rather than merges, so whichever ran last won, and the Go copies had drifted: they dropped the `refresh-client -S` that repaints a client after a window switch, so the client kept mapping mouse coordinates onto the previous window's pane boundaries and clicks went to the wrong pane or nowhere; they dropped the `; true` that keeps a best-effort hook step from reporting failure into every attached client; and on attach they dropped the ensure-daemon, sidebar and geometry steps, so a client reattaching to a session whose daemon had idle-quit came back to a session with no daemon. The three tables are now one, in `internal/tmuxhooks`.

- The daemon no longer renames a window in reaction to its own renames. The Go hook tables registered `after-rename-window` even though `tabby.tmux` documents it as forbidden for exactly this reason: the daemon renames windows itself while refreshing tab titles, so each rename fed straight back into another refresh. Tab titles are unaffected — the daemon drives them on its own schedule, and the user-facing rename paths mark their windows with `@tabby_name_locked`, which is what that hook was standing in for. A stale registration is now actively unset, since a global hook otherwise outlives the binary that set it for the life of the tmux server.

- A tmux server running more than one tabby session stops fighting over window sizes. Every daemon enumerated windows with `list-windows -a`, which spans the whole server, and then locked all of them to its own client's geometry — so a session attached to a phone reflowed the windows of every unrelated session on the same server, and each of those sessions' daemons promptly reflowed them back. Window listing is now scoped to the daemon's own session, which under a grouped family still covers every window it shares.

- The daemon no longer resizes a window that is already the right size. `resize-window` fires `after-resize-pane` and `after-resize-window` whether or not anything moved, those hooks signal the daemon, and the next reconcile re-issued the same resize — a permanent storm of one resize plus one hook per window per cycle, with nothing on screen to explain it. Each of those cycles reflows every window and re-pins the client's focus, so on a phone the button bar came and went and focus moved on its own. The resize planner now skips windows already at the target geometry.

- Killing a tmux session retires its daemon and supervisor instead of leaving them to thrash. The daemon only noticed a missing session on its ten-second idle tick, and the watchdog restarted it up to five times after that — a minute of a daemon reconciling against a session that was not there. The daemon now checks at startup and stops cleanly, and the watchdog stops rather than restarting when the session is gone.

- Hooks stop printing `... returned 1` into every attached client. tmux reports the exit status of a hook body as a message to every client on the session, and a hook fired with no current client has commands that cannot succeed: `refresh-client -S` needs one to refresh. The status of a hook body carries no information anyone acts on, since the work it triggers is a signal to the daemon and the daemon reports its own failures, so every hook now ends in a command that succeeds and the body's own status is left to the scripts it calls.

- Opening a new window no longer bounces you back to the one you came from. The daemon brackets a round of pane surgery by noting which window was current before and restoring it after, so that spawning a header or a sidebar somewhere else does not steal focus. A window created during that bracket is made current by tmux the moment it exists, well before the daemon's cached window list or its own new-window flow have caught up, so the restore read it as focus drifting and undid it. The bracket now adopts the current window when it did not exist when the bracket opened, or when a new-window request is still in flight.

- The phone button bar stops flickering, and focus stops jumping around with it, in a grouped session family. `tmux list-panes -a` walks sessions, and every session in a group links the same windows, so a five-session group reports each pane five times over. The duplicate-header sweep read those repeats as five headers in one window and killed four of them — all the same, only, real pane — leaving the window bare until the next tick spawned a replacement, about a hundred and forty times a minute. Every one of those splits and kills reflows the window and re-pins the client's focus, which is what made focus wander on its own. The header and pane-header sweeps now count each pane once.

  Two related hazards go with it, since several daemons attend the same shared windows: a bar whose owning session and daemon are both still running is now left for that peer to reap rather than killed on sight, the oldest pane wins a genuine duplicate so every peer picks the same survivor instead of each killing a different one, and a daemon whose own client is on a desktop profile no longer tears down a peer's bar while that peer is still serving a phone.

- The layout audit no longer asks for a full refresh twice a second when `pane_header.native` is on. Native mode labels panes through tmux's own border format and deliberately never spawns the overlay header panes, but the audit still counted one missing per content pane and requested the relayout that would never produce them. It now skips that check in native mode.

- A window too short to fit the button bar no longer asks for a full layout refresh every five seconds forever. The spawner declines to split a content pane with fewer rows to spare than the bar needs, but the audit that noticed the missing bar kept requesting the refresh that would never produce one — so a single cramped window drove continuous relayouts across the session. The audit now reports the window as too short and leaves it until it grows.

- A window no longer gets declared finished ten seconds into a long turn. The daemon cross-checks a hook that says "busy" against the pane title, and clears the hook as stale when the title shows no spinner — but a title set by the tool itself never shows one, so every turn on such a pane was called stale, which manufactured a finished-working bell while the tool was still going. The cross-check now reads the pane's progress line before overriding a hook.

- An answered question no longer keeps its `?`. Question detection scanned the whole visible tail of the pane, which holds around forty rows and so usually still shows the last question along with the reply that settled it. The search now starts below the last prompt the user typed into and sent.

- Claude Code's spinner is recognized again, so its panes show activity indicators. Current builds cycle through the half-filled circles ◐◓◑◒ rather than the braille dots tabby was matching, so a working pane read as doing nothing. The knock-on was worse than a missing spinner: both attention indicators are raised when a pane stops working, so a pane that never registered as busy never flagged for input or completion either. Both glyph families are now matched.

- AI tools running over SSH now get activity indicators. The local pane command for a remote session is just `ssh`, so nothing identified the tool inside it and the whole per-pane AI detection pass was skipped — even though the remote tool's spinner and idle glyphs arrive in the pane title like any other. A remote pane whose title carries one is now treated as an AI pane. Nothing needs installing on the remote host.

- Dragging the sidebar border resizes it again when a second terminal is attached. With two clients of different widths on one session, tmux reflows the window to whichever acted last, so the daemon could not tell a drag from a reflow and refused to adopt the new width — while still snapping the pane back to the old one, which read as the drag doing nothing. An unattributable width is now held and adopted once a second pass measures the same width in the same window, and the window you are dragging is left alone until then.

- Reattaching to a session now brings its daemon back. The daemon exits once you detach, and nothing restarted it on the way back in: the reattach check saw a sidebar pane in the window and stopped there, without noticing the pane belonged to a grouped peer session's daemon rather than this one. The session was left with no daemon at all, so the sidebar sat on "Loading..." and every window-navigation key failed against a socket that no longer existed. The check now only counts a renderer this session owns.

- A shared window no longer keeps a sidebar stuck on "Loading...". Grouped tmux sessions share their panes, and only one daemon wins the renderer in each shared window; the losing daemon reaches its idle timeout and exits while its renderer keeps running against a dead socket. The surviving daemon spared that pane because the peer session still existed, so nothing ever replaced it. The peer's daemon socket now has to answer, not just its session exist.

- An unused session no longer respawns its daemon forever. When the last client leaves, the daemon idles out after 30 seconds and signals itself, but that signal was indistinguishable from an external kill, so the watchdog restarted it, it found no clients, and quit again roughly every 50 seconds. Because each life outlasted the restart-count window, the attempt counter reset every time and the watchdog never reached its give-up threshold. The idle path now writes the clean-stop sentinel itself; a daemon killed from outside is still respawned.

- Two sidebars stop fighting over the same panes. A grouped tmux session shares its windows with its peers, so each session's daemon saw the other's renderer panes as orphans from a dead daemon, killed them, and respawned its own — endlessly, which showed up as the sidebar redrawing and focus jumping between windows. A renderer belonging to another session is now only killed once tmux confirms that session is gone; the daemon left without clients idles out on its own.

- The cat stays home when there is something to do. It would head off on an adventure the moment its animation state read `idle`, which happens a frame after you drop food or throw yarn, so a toy could land and the cat would walk away from it. It now waits for an empty yard — no food, no yarn, no mouse, no poop, no unanswered question — and a few seconds of actual idling before it goes (#28).

- `adventure_chance` does something. The key was in the config schema and the documentation but nothing ever read it. It is now the percentage gate on the urge to wander; unset or `0` means 100, which is what the cat has always done (#28).

- The cat is no longer painted over by its own scenery. In both the home scene and the adventure play area the dragon, the yarn, the food and the falling debris were placed after the cat and overwrote it, so the pet you are looking at could vanish behind a passing bird. The cat is drawn last now (#28).

- Crash reports carry the crash. The stack trace goes to the daemon's stderr log, which the report never attached; the events log was read from a path with a dot where the filename has a hyphen, so that section was silently missing from every report ever filed; and the pre-crash forensics quoted whichever `.prev` a size rotation had left lying around, days old, instead of the events the dying daemon had just written. A daemon that restarted five times in six seconds produced five copies of the same stale block and nothing about the panic. The `crash` and `auto-triage` labels are also created if absent, which is what the duplicate-suppression query filters on: without them each crash opened its own issue (#47, #52, #60).

- A session whose name contains `tabby`, `sidebar`, or `renderer` no longer destroys itself on a tmux-resurrect restore. Restored panes get a start command that names the capture file after the session (`cat '…/pane-tabby_session:1.0'; exec -l /bin/bash`), which the pane classifier read as tabby's own infrastructure. Every window then looked empty of real panes and got killed a few seconds after the restore. Classification is now anchored to the program name instead of matching the bare word anywhere in the command line. Thanks to @Corosauce for the diagnosis in #59.

- The sidebar context menu follows the theme. Its text was drawn in a hard-coded `#000000` and its highlight in `#2563eb`, so on rose-pine, catppuccin-mocha, dracula, nord, or any other dark preset the menu was black on near-black. The daemon now sends the resolved palette to the renderer. Where a theme leaves a colour unset the menu inherits the terminal's foreground rather than guessing a literal. Fix contributed by @logicalor in #54, for #53.

- `sidebar.header.height: 0` now actually removes the banner, as do `text: ""` and `padding_bottom: 0`. The loader treated a zero value as an absent key and put `TABBY` / `3` / `1` straight back, so there was no way to turn the header off. These three keys are pointers now, matching `centered`/`active_color`/`bold`, and the defaults resolve at render time. Reported in #58.

- A failed first build no longer leaves a silently dead plugin. `tabby.tmux` checked only for `bin/render-status` before deciding the binaries were present, then discarded the build's exit status, so a machine without a Go toolchain got a plugin that loaded and did nothing. It now checks `bin/tabby` too and reports the failure through `tmux display-message`, with the build log at `/tmp/tabby-install.log`. Reported in #55.

- `make build-linux` says what it is for. It cross-compiles into `bin-linux/` for copying to a remote host; on Linux you still want `make build`, which writes the `bin/` that the plugin loads.

- Nav keys (`M-;` / `M-'`) work in grouped sessions. A session created with `tmux new-session -t <existing>` had no daemon of its own, so every keypress dialed a socket that was never there, hung for the full 1.5s retry budget, and then did nothing. `session-created` and `client-attached` now both ensure a daemon for the session they fire in, via the new `scripts/ensure-daemon.sh`.
